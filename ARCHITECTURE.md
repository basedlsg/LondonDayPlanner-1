# Architecture: London Day Planner

## System Overview

London Day Planner is architected as a **monorepo** containing a unified full-stack application that compiles to multiple targets (Web, iOS IPA, Android APK).

## Directory Structure

```
root/
├── client/             # Single Page Application (React + Vite)
│   ├── src/
│   │   ├── pages/      # Route components
│   │   ├── components/ # Reusable UI
│   │   └── lib/        # Utilities & API clients
├── server/             # REST API (Express)
│   ├── routes/         # API endpoints
│   └── services/       # Business logic (AI pipelines, DB access)
├── shared/             # Code shared between client and server (Types, Zod schemas)
├── ios/                # Native iOS project (generated by Capacitor)
└── android/            # Native Android project
```

## Technical Decisions

### 1. Unified Frontend
We use a **single React codebase** for all platforms.
- **Web**: Served via Nginx/Vercel.
- **Mobile**: Wrapped by Capacitor's WebView. Platform-specific logic is handled via capacitor plugins relative to the `window.Capacitor` object.

### 2. Database & Data Access
- **PostgreSQL**: Chosen for relational integrity between Users, Itineraries, and Venues.
- **Drizzle ORM**: Used for type-safe database queries.
- **Sync**: The app follows an "online-first" approach but caches critical data locally for offline viewing of generated plans.

### 3. AI Pipeline
Itinerary generation is handled server-side to protect API keys and ensure consistent rate limiting.
1. Client sends user preferences (interests, budget, time).
2. Server constructs a prompt for Google Gemini.
3. Response is parsed into structured JSON and validated against a Zod schema.
4. Results are stored in the DB and returned to the client.

## Infrastructure

- **Hosting**: Vercel (Frontend), Railway/Render (Backend).
- **Database**: Neon (Serverless Postgres).
- **CI/CD**: GitHub Actions builds and tests on push; Fastlane handles store submissions.
